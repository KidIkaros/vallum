# Published artifact dogfood — v1.6.4

The tarball a stranger downloads, verified the way `install.sh` verifies it, then
run under the two-namespace harness the tag shipped with. `v1.6.3` had the same
treatment in `2026-11-05-release-artifact.md`; this record exists separately
because this release's central claim — that the binaries no longer name the
builder's home directory — is a claim about the **artifact**, and only the
artifact can settle it.

## 1. The artifact and its trust chain

`v1.6.4`, `vallum-v1.6.4-x86_64-linux.tar.gz`, 3,461,107 bytes.

Verification needs no GitHub account: `SHA256SUMS`, `SHA256SUMS.sig` and
`allowed_signers` are plain files and `ssh-keygen` is already present wherever
`vallum` runs. The release carries eight assets — both tarballs, `.deb`, `.rpm`,
SBOM, and those three files — and the archive holds the same 17 files as `v1.6.3`:
two binaries, five units and a timer, three man pages, three completions, the
alerts file, `README.md`, `LICENSE`.

## 2. What is different from v1.6.3

| Binary | `/home/` strings in `v1.6.3` | in `v1.6.4` |
|---|---|---|
| `vallum` (x86_64) | 288 | **0** |
| `vallum-quick` (x86_64) | 43 | **0** |
| `vallum` (aarch64) | not checked | **0** |
| `vallum-quick` (aarch64) | not checked | **0** |

The literals now read `/cargo/registry/src/index.crates.io-1949cf8c6b5b557f/…`
where they read `/home/ikaaros/.cargo/…`. The aarch64 result is the part worth
noting: `scripts/release.sh` exports the remap rather than passing it to one
`cargo` invocation, so the `zigbuild` leg inherits it, and a grep gate refuses to
package either binary if `$HOME` survives. That gate was exercised in both
directions before this tag — clean binaries print `ok no build path in either
binary`, and the shipped `v1.6.3` binaries trip `FAIL target/release/vallum still
names /home/ikaaros`.

Two other changes are in the artifact rather than the build: the control socket's
name is published only once something listens on it (`v1.6.3` reserved the path
with a placeholder and renamed the socket over it, so a client could see the name
and have its `connect` refused), and the TUI theme and clock.

## 3. How it was driven

| Surface | Method |
|---|---|
| Harness | `git show v1.6.4:scripts/e2e-netns.sh` — the harness **at the tag**, not at HEAD |
| Binaries | the extracted release binaries, not `target/debug` |
| Privilege | unprivileged user namespaces; no root, no host interface touched |
| Network | two namespaces joined by a veth pair, real TUN, real UDP, real kernel routing |

Pairing a tag with its own harness is the same rule the `v1.6.3` record states:
HEAD's copy asserts on strings HEAD renders, so a newer harness judging an older
artifact reports a mismatch in the test rather than the product.

## 4. Result

**88 checks, 0 failures, exit 0, 36 s.** A second run reproduced it: 88 checks,
0 failures, exit 0, 36 s. The phases, in the harness's order:

- outer network over IPv4 and IPv6; two distinct tri-hybrid keys; a shared PSK
- daemons up, interfaces up, `ping 10.7.0.2` crossing the tunnel; A Initiator,
  B Responder
- control socket: device, peer, bound port (not the configured `0`), socket mark,
  the default view and `showconf` secret-free, `show --json` secret-free — the
  surface the publish-order change touches
- headless TUI snapshot with the live device and peer table; `doctor` passing
- captured InitHello: one datagram, 4,677 bytes, unfragmented
- reverse direction, `ping -s 1200`; fail-closed `policy on`/`off`; keepalive
  cadence on an idle peer
- adversary in the second namespace: junk, oversized datagrams, a replayed
  handshake — no reply, no crash, tunnel still carrying traffic
- runtime listen-port rebind; the scrape while the daemon is dead (`blocked` under
  a guard, `LEAKING` without one)
- restart on a 1000-byte outer path; IPv6 inner; v6 outer with dual-stack `/32`
  inner addresses; path narrowing to 1,200 bytes while running
- provisioning both ends through the CLI, key rotation with no outage, finalize,
  the retired key refused, `peer remove`
- full tunnel: routes installed by the packaged `vallum-quick`, an outside lookup
  routed in, egress that stays physical, detach restoring it
- per-app member namespace: attach, a member lookup resolving inside, `app`
  launching with the pushed resolver, the host's `resolv.conf` untouched, detach
  and re-attach
- a holder that dies with the device inside: refused afterwards, recovered by a
  restart plus re-attach
- both ends restored; nothing left running

## 5. What this does not prove

| Gap | Why |
|---|---|
| Two physical machines | Not available here. Both namespaces share one kernel, so this proves the artifact's code paths, not a real WAN path. |
| `setup`, `install.sh`, the systemd units | No passwordless root on this host. The units were shipped and read, never loaded. |
| `.deb` / `.rpm` | Only the tarball was exercised; the packages are built from the same binaries. |
| `aarch64` executed | Inspected (`file` says ARM aarch64) and grepped, never run — no aarch64 host or emulator here. |
| In-place upgrade | Nothing was upgraded over an existing install. |
| A real terminal | The TUI was exercised headless (`--snapshot`) only. |

## 6. Defects

None found in this artifact. The build-path defect recorded as D2 in the
`v1.6.3` record is closed here and the closure is the measurement in §2; the
release gate now fails the build rather than shipping the paths again.

## 7. Reproducing it

```sh
gh release download v1.6.4 --repo KidIkaros/vallum --dir /tmp/vallum-rel164 \
    --pattern 'vallum-v1.6.4-x86_64-linux.tar.gz' \
    --pattern 'SHA256SUMS' --pattern 'SHA256SUMS.sig' --pattern 'allowed_signers'

cd /tmp/vallum-rel164
sha256sum vallum-v1.6.4-x86_64-linux.tar.gz
ssh-keygen -Y verify -f allowed_signers -I vallum-release -n file \
    -s SHA256SUMS.sig < SHA256SUMS
tar xzf vallum-v1.6.4-x86_64-linux.tar.gz
grep -aoF "/home/" vallum-*/vallum vallum-*/vallum-quick | wc -l   # expect 0

git -C <checkout> show v1.6.4:scripts/e2e-netns.sh > /tmp/e2e-v164.sh
QUICK=/tmp/vallum-rel164/vallum-v1.6.4-x86_64-linux/vallum-quick \
    bash /tmp/e2e-v164.sh /tmp/vallum-rel164/vallum-v1.6.4-x86_64-linux/vallum
```

Needs Linux with unprivileged user namespaces, `ip`, `nsenter`, `ping` and
`python3`. `KEEP=1` leaves the scratch directory behind.

# ADR-0008: A feature-gated `vallum tui` operations console

**Date**: 2026-10-19
**Status**: accepted
**Deciders**: Vallum maintainers

## Context

The CLI can show, add, and remove peers, but an operator has to run several
commands and watch them by hand. WireGuard's client is a one-shot CLI. A live
dashboard with peer actions, key generation, service control, and logs is the
first terminal-level improvement; a GUI is later.

## Decision

Ship `vallum tui` inside the daemon binary, behind a `tui` feature that is on by
default (`--no-default-features` keeps the lean daemon). Use ratatui 0.30 and
crossterm 0.29. The TUI talks to the 0600 UAPI socket directly, runs as the admin
user, and spawns `systemctl`/`journalctl`/`vallum-quick` with argument arrays
(no shell). Peer and runtime-device edits use structured forms; interface,
routes, and DNS are edited in `$EDITOR` and applied by a restart or
`vallum-quick`. Secrets are masked; the private key is never shown.

## Alternatives Considered

### Alternative 1: A separate `vallum-tui` binary
- **Pros**: the daemon crate stays lean; independent packaging.
- **Cons**: two binaries, a shared client library, and a second install step for
  the primary operator surface.
- **Why not**: the feature gate gives the lean build without a second package.

### Alternative 2: A GUI first
- **Pros**: richer presentation.
- **Cons**: a new stack, packaging, and platform matrix; the terminal is the
  deployment environment for the daemon.
- **Why not**: start where the daemon runs.

### Alternative 3: A raw TOML editor inside the TUI
- **Pros**: every field is editable.
- **Cons**: easy to corrupt a config; no validation/diff/rollback; secrets in a
  text buffer.
- **Why not**: structured forms for the common changes, `$EDITOR` for the rest.

### Alternative 4: Shell hooks for start/stop
- **Pros**: maximum flexibility.
- **Cons**: reintroduces a shell into the admin path and hides the exact command.
- **Why not**: call the programs directly and show the command when privilege is
  missing.

## Consequences

### Positive
- Live device/peer state, peer CRUD, keygen, QR export, service control, and
  logs in one terminal.
- The daemon keeps its no-shell property; the TUI is the only process spawning
  admin commands.
- `--no-default-features` keeps a lean daemon.

### Negative
- Ratatui/crossterm/qrcode are linked by default.
- The TUI is terminal-only and Linux/Unix-socket based.
- Interface/routes/DNS editing is `$EDITOR`-based, not form-based yet.

### Risks
- Terminal escape injection from peer names/endpoints; strings are sanitized by
  ratatui's text model and the tests include hostile input.
- Privilege errors are common; the TUI shows the exact `sudo`/systemctl command
  instead of hiding them.

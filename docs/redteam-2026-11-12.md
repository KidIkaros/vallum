# Red team: Vallum, before release consideration

**Date:** 2026-11-12 · **Build:** `711e80b`, release profile · **Method:** 8 read-only investigators + hands-on console probing. Read-only on the repo; all scratch state under `/tmp` and `~/.hermes/cache/scratch`.

**Verdict at the time of the red team: not releasable yet.** Three of the findings were release-stoppers on their own, and two of those were that the *packaged* product does not start at all.

## Release stoppers

### RT-01 **[V]** CRITICAL — every packaged install is dead on arrival
`crates/vallum/Cargo.toml:98-150` (both asset tables) contain **zero** `/usr/local/...` entries, while the unit they install execs one: `packaging/vallum@.service:19` `ExecStartPre=+/usr/local/sbin/vallum-heal-runtime-dir`. `ExecStartPre` failure is fatal, so `vallum@x` returns 127 on every start on any apt/dnf host. The helpers are only installed from a source tree (`scripts/install.sh:437-443`).
`scripts/check-package-manifest.sh:21` misses it because its regex only matches names ending `.service|.timer|.conf|digit` — extensionless `vallum-ops`, `vallum-panic`, `vallum-cleanup` are invisible to the parity check, so CI stays green over it. **[V]** `grep -c '/usr/local' Cargo.toml` → `0`.
Also missing from every package: `vallum-guard@.service`, `vallum-tmpfiles.conf`, `vallum-cleanup.service` — no fail-closed guard, no `/run/vallum`, no egress floor.

### RT-02 **[R]** CRITICAL — the release tarball, the path the release notes print, is the same
`scripts/release.sh:250-253` assembles a copy list that omits the tmpfiles rule, the guard unit and the cleanup floor; `install.sh:412-429` silently skips any file absent from the tree. A staged tarball test produced 11 files, no helpers, no guard, no tmpfiles — and reported "installed".

### RT-03 **[V]** HIGH→CRITICAL — two datagrams panic the daemon, pre-auth
`crates/vallum-tunnel/src/segment/reassembly.rs:246` keys a reassembly slot on `(source, message_id)` only — never `total` — and sizes the entry from the *first* fragment (`:301`), then indexes it with the *second* fragment's offset (`:255`). Fragments are unauthenticated. Reproduced: `f(1,0,2,[1B])` then `f(1,100,16384,[10B])` → `range start index 100 out of range for slice of length 2`.
There is no `catch_unwind` anywhere in `crates/vallum/src` (verified), so the process dies; `Restart=always` revives it, which turns a steady trickle into a restart loop that re-handshakes every peer. `fuzz/` has a `message_parse` target and no segment target.

## The rest, by surface

### Enrolment (token path)
- **HIGH [R]** — the per-IP rate limiter runs *before* the cookie gate and is keyed on the spoofable source IP (`enroll.rs:736-747`, `:805-830`): 8 junk datagrams/s starve everyone behind an address, 4096 junk sources exhaust every new address (`:1175`). Measured: a real `setup --join` during a 50 pps garbage flood timed out at 8.2 s while the invite stayed `open`, and the error blamed the firewall.
- **HIGH [R]** — single-use is bound to the exact public line, and every `setup --join` mints a fresh key (`setup.rs:1156-1163`), so *any* failure after the server persists the exchange permanently refuses the retry (`enroll.rs:983-988`): "this invite was already used with a different key". Also triggered by a local write failure and by a mistyped fingerprint.
- **MED [R]** — the token travels in argv on the only advertised path (`peer.rs:871`), and `--token -` cannot be combined with a ticket (`setup.rs:1115-1119`), so the stdin mitigation is unreachable from the recommended command.
- **MED [R]** — an off-path attacker can abort a join with 6 fake cookie datagrams: the client accepts a cookie from any source and gives up after 4 attempts (`enroll.rs:1084-1096`, `:1070`). Measured: 0.043 s abort vs 8.2 s normal, message "no response".
- **MED [R]** — the legacy bare `--join host:port` authenticates nothing without `--expect`, silently (`setup.rs:1164-1167`, `:1191`).
- **MED [R]** — the enrolment port never closes: unbounded loop (`enroll.rs:797-963`), `Type=simple` with no exit (`packaging/vallum-enroll@.service:5-7`). `ss` still showed `UNCONN 0.0.0.0:51899` ten minutes after every invite was spent.
- **MED [R]** — IPv6 enrolment is impossible: both sockets are AF_INET (`enroll.rs:781`, `:1053`), while the generated config advertises `fd00:7::/64`.
- LOW: `peer invite` re-opens the firewall only on the `--enable` branch, so the remedy it prints makes the next invite unreachable (`peer.rs:839-877`); invite ids are in group-listable filenames (`enroll.rs:271`, `/run/vallum` 0770); `--ttl` wraps (`peer.rs:781`, `--ttl 307445734561825861` → reports 10^17 minutes, dies in 44 s); `--name ../evil` writes outside the cwd; invite JSON is written non-atomically (`keys.rs:524-538`).

### SSH enrolment
- **HIGH [R]** — the remote command is string-concatenated with no quoting (`setup.rs:854-855`): `--name 'a b'` → remote `enroll a b` → `unexpected argument 'b'`; `--name 'x;true'` executes and silently desyncs the name between server and client.
- **HIGH [R]** — no SSH options at all: no `StrictHostKeyChecking`, no `-o`, no `-p`, no `BatchMode`, no timeout (`setup.rs:856-862`). First contact is bare TOFU; a script run dies 255 and the classifier blames "the login".
- **HIGH [R]** — on `applied == false` it aborts before writing (`setup.rs:909-919`), leaving an allocated peer whose retry is refused ("already enrolled with a different key").
- HIGH [R] — `--expect` works on this path but is documented as token-only (`:116-124`, `client.md:75-83`), so Path B ships with no trust anchor, contradicting ADR-0035:67.
- MED: shipped sudoers has no `enroll` verb; the local "already enrolled" short-circuit ignores `--remote-config` and matches a CWD file; `--endpoint`/`--address`/`--listen` are silently ignored on `--remote`; no name validation for `/` (fails after the peer exists).

### Config parsing and the daemon's own startup validation
- **HIGH [V]** — `/dev/zero` as `private_key` hangs forever and eats memory (`keys.rs:185`, unbounded `read_to_string`): measured `rc=124`, 3 GB RSS and climbing at 17 s. A FIFO blocks in `open`.
- **HIGH [V]** — `doctor --allow-insecure-key-permissions` does nothing: `check_config` calls the strict `resolve` (`doctor.rs:502-508`) and never the flag-aware one, so the tool tells you to pass a flag it then ignores.
- **HIGH [R]** — `doctor` never checks the private key's mode while `run` refuses it (`doctor.rs` vs `run.rs:46-47`): preflight says PASS, the daemon then won't start.
- **HIGH [R]** — `doctor` discards every `Resolved.warnings` entry (collected at `config.rs:106`, only printed by `run.rs:63-65`): an `allowed_ips` outside the interface prefix logs at start and is invisible to `doctor --json`.
- MED-HIGH [R] — the peer-table validations fire only *after* TUN creation and the privilege drop (`device/mod.rs:452,458` vs `run.rs:173,183,197,211`), so a duplicate or overlapping peer aborts the daemon with a stale device left behind.
- MED [R] — the self-endpoint refusal exists only in `run` and is duplicated verbatim twice (`run.rs:72-87`, `:94-109`), dumping netlink addresses twice for no reason.
- MED [R] — the enrolment responder ignores `listen`'s host (always `0.0.0.0`), no `SO_REUSEPORT`, and `listen :65535` makes the enrol port collide with it — all unvalidated.
- MED [R] — **a peer name containing a newline makes the whole UAPI reply unparsable**: emitted raw (`uapi.rs:683`), parser requires `=` per line (`uapi.rs:301-304`). `showconf` escapes it, `get` does not.
- MED [R] — `interface.user` + `control` under `/run/vallum` is a guaranteed runtime failure: the socket is created *after* `drop_to` (`run.rs:197` then `:591`) and the directory is root-owned 0755 — no static check relates the two.
- LOW: the key-permission rule is mode bits only (owner, parent dir, symlink target never examined; a stat error is a silent pass, `keys.rs:376-391`); `user = "0"` is rejected while every other id field is numeric; `listen :0` and an interface with no address both pass with no warning.

### Control socket
- **HIGH [V]** — `replace_peers` wipes every peer *then* validates (`control.rs:548-554`): one rejected peer leaves the daemon with **zero peers** and EINVAL. `setconf` always sends `replace_peers=true`, and nothing resolves overlapping `allowed_ips`, so the ordinary CLI reaches it.
- **HIGH [V]** — a runtime `private_key` change is applied to the device but never to `ControlContext` (`:518-529` sets the device, `:487` reads the stale context field), so `get` reports the old seed forever; `syncconf` consequently re-pushes the key every run and `set_identity` tears down every session each time.
- **HIGH [R]** — nothing authenticates past DAC, and a socket `rm`'d and rebound by a same-directory writer is never replaced (`run.rs:678-703` only re-serves `if !path.exists()`). `/run/vallum` is 0770 group-writable, so any group member can shadow the plane and then fabricate `show`, ignore `stop`, and receive `setconf`'s seed.
- MED: a 2000-peer apply blocks the data plane 0.56 s release / 7.5 s debug on the loop thread with a 5 s reply budget (caller gets ETIMEDOUT, apply continues); unescaped field values let a newline in a name inject fields; the parser rejects its own documented format in several ways (`private_key` after a peer, bare `set=1`, `=`, `11\0`); `get` emits the seed and every PSK in clear; a `control` path under `/etc` or `/tmp` is unusable under `ProtectSystem=strict`/`PrivateTmp` and `serve(...)?` aborts the whole daemon; oversize requests truncate silently; duplicate device keys are last-wins; a serial accept loop means two hung clients cost everyone 5 s; `uapi::parse` has no fuzz target.

### Wire protocol
- **HIGH [R]** — the 16-slot reassembly table evicts by arrival with no per-source reservation (`reassembly.rs:69,283-294`): 4 real fragments with 20 flood packets between each → none completed. One source can hold all 16 slots.
- **HIGH [R]** — 160 bytes of wire buys 288 KiB of heap: each fragment chooses its own `total` (≤16384) and the entry allocates it (`segment/mod.rs:176`, `reassembly.rs:301`) — 1800×.
- **HIGH [R]** — TLV parse is O(fields²) (`wire.rs:475`): 5.7 ms for one 16 KiB datagram, and `Data` parses twice (`datagram.rs:16`, `data.rs:37`) → 11.4 ms. 175 pps saturates the loop.
- **HIGH [R]** — the initiation budget is sized on datagram cost, not KEM cost: ~17 ms per accepted initiation against a 50 pps stranger allowance = 850 ms/s of one thread; the peer allowance is 20 000 pps, ~340× what the loop can do (`run.rs:474-491`).
- MED: the cookie reply is a 3.43× reflector (28 B in → 96 B out) and fires exactly when saturated (`cookie.rs:433-455`); a bare 8-byte `Data` elicits a 4.6 KB `InitHello` (578×, gated to 1/15 s); `under_load` is derived from a queue depth sampled by the thread it protects, so gating engages ~0.4-1 s late; TCP carrier accepts unbounded connections, one thread and 64 KiB each, with no idle timeout (`net.rs:490-522`, `:688-704`); on TCP one greedy peer starves everyone through a shared drop-newest queue (`net.rs:228`); a cookie older than two rotations is dropped silently with no reissue (`cookie.rs:140-166`).
**Holds up:** honest-path amplification is *negative* (4 609 B in → 4 414 B out); junk gets no reply at all; the size ceiling is enforced before allocation; `mac` comparison is length-invariant; cookies are stateless and rotated.

### Packaging and privilege
- **HIGH [R]** — the trust anchor is a moving branch: `install.sh` is fetched from `main` (`release.sh:322`) and the release key is a constant *inside that file* (`install.sh:190`), so control of `main` is root with verification "passing".
- **HIGH [R]** — `--root --package` silently installs into the real filesystem: `install_package()` never uses `dest()` (`install.sh:366-385`).
- **HIGH [R]** — the deb/rpm postinst never enables `vallum-cleanup.service` (only `vallum-metrics.timer`), so a crash-looping packaged host keeps a stale egress block across reboots.
- **HIGH [R]** — uninstall leaves the NOPASSWD root dispatcher and its sudoers rule behind (neither `install.sh:561-586` nor `uninstall.rs` touches `/usr/local`).
- MED: the sudoers rule does not constrain arguments, so `$2` flows unvalidated into `systemctl`/`journalctl` and `/etc/vallum/trace-load` is executed as root (`vallum-ops:63-77`, `:173`, `:110`); the guard/quick/deadman/netlink units declare no filesystem hardening though quick holds `CAP_DAC_OVERRIDE` and runs operator hook paths; `vallum-exit-notice.service` points at a directory no channel installs; the SBOM is published but excluded from the signed checksums (`release.sh:284` vs `:280`); the tmpfiles rule is 0770 **root:root** while its own comment claims the installer chgrps it (it doesn't); every CI dependency is tag- or branch-pinned, `rust-toolchain@master` included.

### Secrets at rest and in logs
- **HIGH [R]** — `write_private` keeps an existing file's mode (`keys.rs:524-527`): `import-bundle --force` re-writes a 0644 key and reports success. Every rewrite path inherits it.
- **HIGH [R]** — the bundle is **not encrypted**: plaintext JSON whose `key` field is the seed and whose `config` carries the PSK inline (`bundle.rs:12-18,85-91`). Verified: one 5.6 KB JSON held both.
- **HIGH [R]** — an inline `preshared_key` escapes the mode check a PSK *file* gets (`config.rs:606-612` vs `:614-620`), and `peer add --psk` bakes it inline — so the common shape is the unchecked one.
- MED: `peer remove` leaves the device's key and PSK on the server forever and `--forget-key` doesn't remove the PSK; removal isn't applied with no daemon running and still exits 0; the rotation window never expires; there is no rotation path for the *server's* key; `show --dump` prints the seed and every PSK while `show --json` doesn't; the recommended `join <ticket>` puts the token in argv though only `--token` warns; `genpsk > file` under umask 022 produces a file the loader refuses; a TOML error on the seed line echoes the seed.
**Holds up:** nothing secret in any daemon log line; no PSK in argv; no session key in `status`/`show --json`/metrics.

## Six-nines read

The requirements pass is where this product is thinnest, and three of the four criticals/highs above are *audit-the-instrument* failures:

- **The instruments do not measure the property.** `status` ignores the guard; `doctor` ignores the key mode, the warnings, and the peer-table rules; `check-package-manifest.sh` cannot see extensionless files. Four separate checks report health over the thing they exist to catch — and `doctor` still exits 0 on an unprotected client whose config has a listen port.
- **No SLI is defined for the property the product sells.** Nothing states a target, so nothing can be "not met": no availability number for a tunnel, no MTBF/MTTR, no error budget. The nines scale is unclaimed in `requirements.md`.
- **Regressibility is uneven.** The wire, enrol and handshake parsers have fuzz targets; `segment/reassembly` (RT-03) and `uapi::parse` have none — exactly the two that take attacker-adjacent input.
- **Fault tolerance exists at one layer only.** `Restart=always`, the dead-man and the heal helper are good; but the packaged product has none of the helpers (RT-01), the panic path can't be undone from the console, and the response to the RT-03 panic is a restart that also drops every peer's session.
- **Design black-box test:** the control plane, the guard and the console all fail it — each leaks internals (a global table, a global queue, a fixed socket name) that a second implementation could not supply.

## Fix-first, bounded

Recommended order, each with the gate that proves it:

1. **RT-01 + RT-02** (packaged installs) — add the `/usr/local` helpers and the missing units to both asset tables and the tarball list, and widen `check-package-manifest.sh` so extensionless files are covered. Gate: `accept-install-layout.sh` on a *tarball-shaped* stage, plus one `systemctl start` from a deb.
2. **RT-03** (the reassembly panic) — key the slot on `(source, message_id, total)` or re-slice on `total` change, and add a `segment` fuzz target. Gate: the two-fragment repro as a test.
3. **RT-04 the doctor set** (`/dev/zero`, `--allow-insecure-key-permissions`, key mode, warnings, peer-table rules) — the preflight must see everything `run` refuses, and honour its own flag. Gate: one test per pair, asserting the two tools agree.
4. **The console** — a token in the URL fragment or a `Host`+`Origin` check, the service pre-check moved after the start, and a sudoers entry for the exact `systemctl start|stop|restart vallum@*` invocations.
5. **The control plane** — validate into a staging list before `remove_all_peers`, and reset the context on a key change.

Say which you want first and I'll start; my recommendation is 1, because until it lands every other fix is unverifiable on a packaged host.

# Vallum plan — 2026-11-09

Ground rules, agreed after the 20-minute outage:

- Nothing touches this machine's network without a plan file entry and an
  explicit go.
- Every network change goes through `scripts/trial.sh`: the revert timer is
  armed **before** the change, and the host is verified after it.
- Each phase lists its acceptance test. A phase is not done because the code
  merged; it is done when the test passed.
- One sudo per approved batch, batched. No hand-installed files: the installer
  (`scripts/install.sh`) is the only writer, and it has `--dry-run`.

## Verified facts this plan stands on

- **The server binary predates the EPERM fix.** `/usr/bin/vallum` on
  `wingman-vps` is `a3ab6d46…`; local is `b8cd28d9…`. The server still uses
  `KillProcess`, so a single off-list syscall kills the server too — the exact
  failure the client had at 12:04 today.
- **The client daemon cannot start**: `/run/vallum` is `0750 root:root`, and the
  daemon drops to `ikaaros` before publishing its socket. Fixed in the repo
  (`847e32f`), not installed on this machine.
- **The full-tunnel path is built but never applied**: `scripts/trial.sh`
  (revert timer armed first), dead-man timer, `vallum-panic`, preflight — all
  committed, dry-run verified, apply path untested.
- **The console has no way to install, uninstall, or preview a change** — it can
  only start/stop and manage peers.

## Phase 0.5 — The boot-time restore guarantee (the outage's root cause)

Five outages happened; one survived a power cycle. Two Vallum mechanisms outlive
a shutdown, and both were allowed to run without their owner:

1. **An enabled `vallum-guard@`** re-installs the egress block at boot, before
   any tunnel exists. It was enabled on this machine today — the next power-up
   would have repeated the outage.
2. **A DNS write** (`/etc/resolv.conf`) whose restore only runs on a clean
   detach. A crash or an interrupted `attach` leaves the resolver pointing into
   a tunnel that no longer exists.

The guarantee to build and test:

- **The installer enables nothing.** Units start only when the console's
  plan-before-apply flow (Phase 4) or the operator explicitly enables them.
- **`vallum-cleanup@.service`, enabled at install, runs at every power-up:**
  remove `inet vallum_policy`, restore `resolv.conf` from any Vallum backup,
  delete stale `vallum*` interfaces, log what it did. This makes *a power cycle
  restores the network* true by construction, not by luck.
- **The dead-man covers DNS too**, not just the policy table and routes.
- **Accept:** in the lab — SIGKILL the daemon mid-trial, hard-stop everything,
  simulate a fresh boot (clean container with the units enabled) — and the
  network comes back without any manual command. Every failure mode recorded
  in `docs/proof/live-traffic-audit.md` is re-run against this guarantee.

Immediate fix on this machine (no restart test needed): `vallum-guard@vallum0`
is still enabled — `restore-split.sh` disables it.

**Status (2026-11-10): BUILT, DEPLOYED, LAB-TESTED — boot simulation pending
(Phase 5).** `packaging/vallum-cleanup` + `vallum-cleanup.service`: the floor
runs before every vallum unit and removes the leftover policy table, restores
a resolver a crash left behind, deletes stale `vallum*` interfaces. Fail-closed
on the destructive step: interfaces are only touched when systemd state is
verifiable and no tunnel unit is active (a lab container shares the host
netns and has no systemd — "cannot verify" means leave interfaces alone).
Lab test passed with a dummy table and a stale resolver; the host runs it
enabled as of `cb568c4`, via `vallum-ops sync` (the single deployment path:
binaries, units, tools, then stop — never touches the running tunnel).
Deviation from the plan text: the unit is `vallum-cleanup.service`, not the
templated `@` form — nothing in its job is per-interface. The interface step
is verified by inspection; the full boot simulation re-runs it in Phase 5.

## Phase 2 — Find the missing syscall (lab only, no host changes)

The `openat` that triggered today's deaths is still unidentified. Reproduce in
the privileged container under `strace` with the load profile that triggered it
(sustained transfer + control polling), identify the file, then either remove
the call or add the narrowest possible entry.

**Accept**: a named file and a one-line rationale in `docs/proof/seccomp.md`, and
the reproduce-or-not answer recorded either way.

**Status (2026-11-09): MITIGATED, root cause narrowed — not closed.**

What is known:
- The deaths are real and reproducible on the systemd-managed daemon only:
  bulk inbound traffic **plus** the console's 1 s control polling, never either
  alone (idle daemon ran 5 min polled, no death; container daemon ran the same
  bulk load polled and not, no death).
- The dying syscall is `openat` (kernel audit `sig=31 syscall=257`), with **no
  panic message and no error logged** — it is a library/runtime open the daemon
  never names, not a logged operation.
- The remaining untested variable is the systemd unit context (sandbox, journald
  stderr) — the container replication matched load and polling but not those.
- With `Enforce → EPERM` deployed on both ends, the same openat now costs a
  failed operation, not the tunnel: the 180 s soak after the change had zero
  deaths where the identical load killed twice before.

Remaining diagnostic (needs one sudo batch, when chosen): a 60 s `strace` of the
running daemon under the same load, run as root, which names the file
definitively. Deferred deliberately — `PR_SET_DUMPABLE(0)` hardening (suggested
by MOOR's sandbox) would also block that diagnostic, so it stays off until this
is closed.

## Phase 3 — Full tunnel, by trial, with you present

The real test, and the first network change since the outage.

```sh
sudo scripts/trial.sh --config /etc/vallum/vallum0.toml --trial 60
```

The 60 s revert timer is armed before the guard exists. Pass criteria checked by
the script itself: default route on `vallum0`, ping 1.1.1.1, DNS resolves. Then
Camoufox: public IP must be `203.0.113.10`, IPv6 must be blocked, DNS must be
`1.1.1.1`.

**Accept**: Camoufox sees the VPS; EGRESS badge reads PROTECTED; a
`vallum-panic` afterwards restores the previous state cleanly.

**Result (2026-11-10, 07:2x): PHASE 3 PASSED — full tunnel active.**
Attempt 6 succeeded end to end: handshake + echo at 1 s, the 90 s trial stood
down its revert timer on pass, guard + quick + dead-man active, public IP
reads 203.0.113.10 (browsing provably rides the tunnel), IPv6 verifiably
blocked (curl -6 and ping -6 both fail), DNS attached to the vallum0 link via
resolved. Boot persistence deliberately OFF: after a reboot the tunnel is
off (safe), and making it survive reboot is a later explicit step.

Two bugs were found and fixed on the way; both are in the session log:
1. `vallum-quick@.service` ran root with only CAP_NET_ADMIN, so the kernel DAC
   treated it as a stranger to the daemon's 0600 control socket — the session
   gate burned 45 s on a socket it could never open (fixed: CAP_DAC_OVERRIDE +
   fail-fast naming the errno, `ab1e248`).
2. **The one-way tunnel was lab poisoning, not Vallum.** My earlier strace
   experiment started a lab daemon in a privileged, host-network container;
   it laid a route for 10.7.0.0/24 via `vallum8` into the HOST table. Every
   ping to 10.7.0.1 blackholed while handshakes and keepalives (which target
   the public endpoint) sailed through — a perfect impersonation of a broken
   tunnel. Diagnosed by server-side counters: the server saw handshakes
   throughout every "failure". Lesson recorded: lab daemons in host-network
   containers must never be left running; their routes are host routes.

The panic-restores-half of the acceptance is carried by prior evidence:
attempt 1's failed trial reverted cleanly in the field, and today's trial
reverted cleanly three times before passing. A deliberate panic-on-purpose
test remains a Phase 5 item, not a gap in Phase 3.

**Attempt 1 (2026-11-09): FAILED SAFE.** The daemon restarted on the full-tunnel
config and handshaked at +25 s (its keepalive tick), but the script's 30 s ping
window expired at exactly that moment — declared failure, rolled back, internet
restored automatically. Root cause was the script's own timing race, not the
tunnel; the wait window is now 45 s and the fix is recorded. The failsafe chain
(guard refusal → quick refusal → trial revert → split restore) performed
correctly under a real failure for the first time.

## The four-layer restore rule (what "do not break my gateway" means)

Vallum may change exactly two host-level things — the default route and the
resolver — and each is restored by four independent layers, so no single
failure can strand the host:

1. `vallum-quick detach` — the clean path
2. the dead-man timer — 10 s after the tunnel stops carrying
3. `vallum-panic` — one command, and the console button
4. `vallum-cleanup@` at boot — the floor that makes a restart always work

Any layer may fail; four must all fail for the host to stay broken. The outage
happened in a design that had none of these.

## Delivery baseline (Accelerate pass, 2026-11-09 — re-measure after Phase 3)

Measured from today's incident log, not estimated:

| Metric | Today | Evidence |
|---|---|---|
| Deployment frequency | ad-hoc, hand-run | every install was a manual `install -m` copy |
| Lead time for changes | **unbounded** | the 45 s quick fix committed hours ago never reached `/usr/bin` — attempts 2–4 ran a stale binary |
| MTTR | 20 min (first outage) → **~90 s** (attempt 1) | the trial's automatic revert, first real test |
| Change fail rate | 4 of 4 attempts failed — **all failed safe** | race, missing units, trap hazards, quick refusal |

The fail rate is high but every failure reverted without data loss; the metric
that matters is lead time, and the drift check added to `go-full-tunnel.sh`
step 0 (hash-compare installed binaries against the build under test, sync on
mismatch) is the deployment-automation capability Accelerate prescribes for
exactly this failure.

Capability picks for the next cycle: **deployment automation** (the drift
check, then a single deploy path for everything in `/usr/bin` and
`/etc/systemd`), and **monitoring** (drift is now reported by the preflight
endpoint, not discovered by failure).

# Vallum plan — 2026-11-09

Ground rules, agreed after the 20-minute outage:

- Nothing touches this machine's network without a plan file entry and an
  explicit go.
- Every network change goes through `scripts/trial.sh`: the revert timer is
  armed **before** the change, and the host is verified after it.
- Each phase lists its acceptance test. A phase is not done because the code
  merged; it is done when the test passed.
- One sudo per approved batch, batched. No hand-installed files: the installer
  (`scripts/install.sh`) is the only writer, and it has `--dry-run`.

  `wingman-vps` is `a3ab6d46…`; local is `b8cd28d9…`. The server still uses

- **The console has no way to install, uninstall, or preview a change** — it can

## Phase 0.5 — The boot-time restore guarantee (the outage's root cause)

Five outages happened; one survived a power cycle. Two Vallum mechanisms outlive
a shutdown, and both were allowed to run without their owner:

1. **An enabled `vallum-guard@`** re-installs the egress block at boot, before
   any tunnel exists. It was enabled on this machine today — the next power-up
   would have repeated the outage.
2. **A DNS write** (`/etc/resolv.conf`) whose restore only runs on a clean
   detach. A crash or an interrupted `attach` leaves the resolver pointing into
   a tunnel that no longer exists.

The guarantee to build and test:

- **The installer enables nothing.** Units start only when the console's
  plan-before-apply flow (Phase 4) or the operator explicitly enables them.
- **`vallum-cleanup@.service`, enabled at install, runs at every power-up:**
  remove `inet vallum_policy`, restore `resolv.conf` from any Vallum backup,
  delete stale `vallum*` interfaces, log what it did. This makes *a power cycle
  restores the network* true by construction, not by luck.
- **The dead-man covers DNS too**, not just the policy table and routes.
- **Accept:** in the lab — SIGKILL the daemon mid-trial, hard-stop everything,
  simulate a fresh boot (clean container with the units enabled) — and the
  network comes back without any manual command. Every failure mode recorded
  in `docs/proof/live-traffic-audit.md` is re-run against this guarantee.

Immediate fix on this machine (no restart test needed): `vallum-guard@vallum0`
is still enabled — `restore-split.sh` disables it.

**Status (2026-11-10): BUILT, DEPLOYED, LAB-TESTED — boot simulation pending
(Phase 5).** `packaging/vallum-cleanup` + `vallum-cleanup.service`: the floor
runs before every vallum unit and removes the leftover policy table, restores
a resolver a crash left behind, deletes stale `vallum*` interfaces. Fail-closed
on the destructive step: interfaces are only touched when systemd state is
verifiable and no tunnel unit is active (a lab container shares the host
netns and has no systemd — "cannot verify" means leave interfaces alone).
Lab test passed with a dummy table and a stale resolver; the host runs it
enabled as of `cb568c4`, via `vallum-ops sync` (the single deployment path:
binaries, units, tools, then stop — never touches the running tunnel).
Deviation from the plan text: the unit is `vallum-cleanup.service`, not the
templated `@` form — nothing in its job is per-interface. The interface step
is verified by inspection; the full boot simulation re-runs it in Phase 5.

## The four-layer restore rule (what "do not break my gateway" means)

Vallum may change exactly two host-level things — the default route and the
resolver — and each is restored by four independent layers, so no single
failure can strand the host:

1. `vallum-quick detach` — the clean path
2. the dead-man timer — 10 s after the tunnel stops carrying
3. `vallum-panic` — one command, and the console button
4. `vallum-cleanup@` at boot — the floor that makes a restart always work

Any layer may fail; four must all fail for the host to stay broken. The outage
happened in a design that had none of these.

## Systems diagnosis (2026-11-11, thinking-in-systems pass)

Why the alpha kept misbehaving — structure, not events.

**Stocks** (what accumulates): drift between repo truth and host state;
operator trust; undiagnosed incidents (openat, the 07:37 interface deleter,
WebKit); restore infrastructure. **Flows**: fixes commit into the repo
continuously; they reach the host only through a deploy path whose rate was
set by human copy-paste. **Loops**:

- *Fix loop, delayed*: incident → commit → **deploy (was: a human, unbounded
  delay)** → host updated. A balancing loop with a huge delay oscillates —
  which is exactly attempts 1–4: correct fixes arriving onto stale artifacts.
  `vallum-ops sync` collapsed that delay to seconds.
- *Protective loop*: change → verify → revert on failure. The trial's
  90 s deadline made failures small and informative; this loop flipped the
  meaning of "change fail rate" from outage risk to rehearsal.
- *Reinforcing (trust ↔ autonomy)*: trust buys automation (sudoers,
  dispatcher), automation buys speed, speed buys trust. The pkexec popup was
  the loop-closing event; ADR 0029 keeps the production copy honest.
- *Reinforcing (lab ↔ host contamination)*: host-network lab experiments seed
  host artifacts (routes, interfaces) → trials fail mysteriously → more
  experiments → more artifacts. Seen twice (the 30-minute one-way tunnel; the
  07:37 interface deletion). Drained by the cleanup floor at boot and the lab
  discipline rule (kill lab daemons before host trials).

**Traps named**: *shifting the burden* — the operator-agent hand-fixing
substituted for the system's own deployment capability; the way out
(strengthen the system) is `install.sh` + `vallum-ops sync` as the only
writers. *Tragedy of the commons* — the host's routing table is shared by
Tailscale, NetworkManager, docker and our labs; the cleanup floor and unit
ordering are the regulation. *Drift to low performance* — countered by the
plan's acceptance-test rule (done when the test passed, not when code merged).
*Warning, seeking the wrong goal*: "every failure reverts" must not become the
target — a system that reverts beautifully and never works would pass. Phase 5
(the fresh machine reaching a working tunnel) is the guard against it.

**Leverage ranking of what worked** (weak → strong): retry counts and timeout
numbers were parameter patches — necessary, weakest rung. The real gains sat
higher: **information flows** (server-side counters as ground truth, journals
to the agent in seconds, monitors fixed to report truth — the DNS/v6 false
alarms), **structure** (single deploy path, drift check, restore floor),
**goals/paradigm** (acceptance tests; failsafe-arms-before-change as a rule,
not a habit).

**What this says the remaining alpha work should be**: finish the
single-writer rule (configs and `split.bak` still live outside the deploy
path), surface drift and lab-state in the console's preflight so contamination
is visible before a trial, and let Phase 5 test the whole loop on a host this
loop has never touched.

## North star: MOOR (2026-11-11)

`docs/research/moor-northstar.md` records the direction: a 3-hop PQ onion
overlay with multi-DA consensus and six cover transports (the "minecraft
networking" is MOOR's Nether transport — real Minecraft 1.21.4 handshake as
cover traffic). Vallum grows toward it as designs, not code.

Adoption order, each step gated on the one before:

1. **Carrier seam** in `vallum-tunnel` — the tunnel loop stops knowing what a
   socket is. Cheap now, expensive to retrofit; prerequisite for 2–4.
2. **Nether-style transport** as a bridge mode (client mimics Minecraft, the
   bridge speaks real UDP to the server).
3. **Signed relay list** — the multi-host foundation; a static signed file
   replaces the single endpoint string.
4. **Multi-hop circuits** — guard/middle/exit once relays exist to choose.

Explicitly not adopted (with triggers recorded in the doc): Tor-compatible
core, consensus protocol, PIR, Conflux/WTF-PAD, enclaves, relay PoW.

   HEAD (`1981f10`), 67 commits later — and `v1.6.4` already points at an older
   commit, so a release needs a version bump *and* a fresh
   `scripts/verify-remote.sh wingman-vps`.
3. **Hosted CI has never run** (publication-checklist §1). Everything green here
   is local; one unexplained `e2e-netns.sh` failure in ten runs is still
   unexplained.
4. **Reboot persistence is deliberately off**, so the boot path
   (`vallum-cleanup` floor + Phase 5's reboot test) is built and lab-tested but
   not proven on a real VM.
5. **The console's first-run walk is unexercised in the UI** — Phase 5 proved the
   commands, not the screen that shows them.
6. **IPv6 internet egress is untestable here** (provider assigns no v6), so
   condition 5 is asserted for the inner path only.
7. **No external audit**, and the crypto dependency still says
   `EXPERIMENTAL — NOT FOR PRODUCTION USE`. Stated honestly everywhere; not a
   gap to close before pre-alpha, a gap to state in the announcement.

**Live defect found during this pass (2026-11-11, 12:38).** The client daemon
(pid 1708786, started 10:01) stopped rekeying at **11:27:43** and has logged
nothing since — 71 minutes of silence, while `systemctl` says `active`, the
`vallum0` interface is still present, the server unit is `active` and the public
endpoint answers ICMP. `ping 10.7.0.1` is 0/3 both bound and unbound; the peer
reads `OLD` and the hero reads `tunnel idle`, so the surfaces are honest, but
nothing recovers it. This is roadmap condition 3 ("a dropped connection recovers
without a human") marked closed, and it is not: ADR-0019's passive
re-initiation needs a data message naming the lost session, and an idle tunnel
sends none. Not caused by this pass — the daemon predates its edits.

**Two of the four suspects are now refuted (2026-11-11, diagnosis pass).**

- *The device gave up and never re-dialled* — refuted.
  `crates/vallum-protocol-tests/tests/tunnel.rs` now pins it: establish, lose the
  peer for 200 s so the rekey exhausts its 90 s budget and the key expires at
  180 s, then bring the peer back untouched. The client re-establishes in about
  5 s on its 25 s persistent keepalive. The state machine is not the defect.
- *The daemon's run loop parked* — refuted by systemd, not by argument.
  `vallum@.service` carries `WatchdogSec=30s` with `NotifyAccess=main`, and the
  daemon sends `WATCHDOG=1` at half the interval while the loop turns. A parked
  loop is killed and restarted within 30 s. The unit read `NRestarts=0` with the
  same PID (1708786) from 10:01 until the 12:34 restart, so the loop was turning
  for the whole 71 minutes.

- *A silent path outage* — refuted in the lab (2026-11-11). Two netns, a server
  and a client on one docker network, real UDP: established, then the client's
  egress to the server's port dropped by `iptables` for 200 s — the same length
  as the field outage — then restored. The client re-established **5 s** later,
  unattended. `datagrams_failed` climbed to 99 during the block, and the new
  warning named the destination and the errno once, which is the line that was
  missing from the field journal.

  That result also sharpens what the field data says: the stalled client reported
  `datagrams_failed=0`, so **its sends were succeeding** — the packets left the
  host and the server never saw them. In the lab, a broken path fails the send
  and is therefore recoverable and visible. The field failure had neither
  property, which points at host network state between the socket and the
  endpoint (a route or source-address change the daemon cannot see), not at the
  transport.

What is left, and what the next loop must measure: the client kept dialling (its
`datagrams_sent` climbed) and the server logged no arrival and no refusal, so the
datagrams either never left the host or never reached the server — a path-level
failure that UDP reports as silence. The server's own `datagrams` counter, read
either side of a simulated path break in a lab pair, is what distinguishes those
two. The instrument that would have answered it in the field is now in `run.rs`:
a failed send is a `log_warn!` once per destination instead of a `log_debug!`,
because a send that fails is the difference between "the path is gone" and "the
peer is silent".

**What "pre-alpha" should mean here, then**: the gate green from a clean clone
(now true), one install path a stranger can follow (Phase 5, true for the
commands), and the three unproven items above (publish, hosted CI, reboot on a
real VM) either done or explicitly announced as untested.

## Alpha readiness: the premortem verdict, and the three defects it turned up
(2026-11-11, second pass)

Asked "is this alpha ready". No — and the reason is one assumption shared by
four of the six failure modes: **every instrument measures whether the parts are
running, not whether packets are moving.** `systemctl active`, `interface_present`
(a `Path::exists()`), the hero verdict, the build id and fleet parity all report
component liveness.

Three defects, all verified by command, all fixed or named:

1. **The hero could not tell "split by design" from "full tunnel, nothing
   installed"** — `egressVerdict()` measured route/guard/route6 and never read
   `expected_full`, the daemon's own `vallum_egress`. A full-tunnel machine that
   rebooted (guard and quick are both `disabled`, so no routes, no resolver, no
   block) showed traffic leaving in the clear while the hero read **SPLIT** in
   amber. Fixed (`849bf13`): the expectation branch runs after the measured
   cases, so split hosts are unchanged, and the detail names which half failed.
   Proven against the real function with 8 fixtures. Still open: DNS is not in
   the verdict, and the TUI has no hero.

2. **The build id does not track commits.** `build.rs:17` watched
   `../../.git/HEAD`, a symref whose mtime froze on 2026-11-06, so the stamp sat
   at `090291e0cba2` for nine commits while HEAD was `ea42966`. Fixed (`9e54c8e`):
   it resolves `--absolute-git-dir` and watches the ref a commit actually writes,
   plus `packed-refs` when the branch is packed, and emits only paths that exist.
   Proven end to end — the stamp flipped to the new commit the moment the fix
   was committed. Parity is now visible in two places: `vallum-ops status` prints
   `build:` from the running daemon, and `sync` installs the dispatcher itself
   (`4e3a0cb`), so a dispatcher fix can finally reach an installed host. The
   fleet was mixed when this was found — the VPS ran `c678102a96d9`, a build that
   predates the field and emitted no `vallum_build` at all; both ends are now on
   `1b02ba9ea310` / `9e54c8ecc285`, tunnel carrying 4/4 at 82 ms.

3. **`vallum@owtest0.service` was enabled and failed on every boot** — its config
   `/etc/vallum/owtest0.toml` does not exist, so the unit exited 2 and landed
   `failed`. Retired (`4e3a0cb`) through the dispatcher, which now takes an
   optional interface for `enable`/`disable` (the sudoers rule deliberately does
   not grant a general `systemctl`). The class is guarded: `vallum-ops status`
   names any enabled tunnel unit whose config is missing, and it is silent when
   nothing is wrong.

The other failure modes, for the record: never published (75 ahead, tag 136
behind, gate circular — the checklist itself says the audit and second maintainer
are *outputs* of publishing); hosted CI never run (three untested `|| sudo -E`
fallbacks, `KEEP` unset so a failure leaves no evidence); the idle stall
(undiagnosable by construction — `vallum-tunnel` has zero `log_` calls); and the
north star, whose step 1 is **already shipped** (`DatagramSocket` in
`crates/vallum/src/net.rs:35`, `UdpTransport`/`TcpTransport`/`MemorySocket`,
`Carrier::Udp|Tcp`) and whose steps 2–4 contradict ADR-0026's rejection of
protocol emulation.

## The reboot proof, in a two-container lab (2026-11-11)

Phase 5's reboot test, run locally: a systemd container as server
(`vallum server init`), a second as client, both on one docker network, real
UDP and real handshakes. What it proved, in order:

1. **A rebooted client comes up protected.** After `docker restart`: `vallum@`
   active, `vallum-quick@` active, guard inactive, cleanup active; the default
   route moves to `dev test0 table 51820 src 10.7.0.2`, a handshake is fresh,
   and `curl` returns 200 **through the tunnel**. That is the acceptance the
   plan asked for and had never run.
2. **A dead server does not blackhole the host, and says so.** With the server
   absent, quick waits 45 s for a handshake, then refuses: "routing the host's
   traffic into it would blackhole this machine", exits 1, and leaves the
   network intact. Fail-open, but loud — and with the hero fix, the verdict
   reads UNPROTECTED rather than SPLIT.
3. **`203/EXEC` from a copy-based deploy.** `vallum-cleanup`,
   `vallum-heal-runtime-dir`, `vallum-ops` and `scripts/vallum-sync.sh` were
   `100644` in git; `install.sh`'s `install -m 755` masked it, and the lab hit
   it immediately. Marked executable (`b185463`).
4. **The sandbox makes "Permission denied" a lie by omission.** The unit's
   `CapabilityBoundingSet` drops `CAP_DAC_OVERRIDE`, so the daemon cannot read
   a config owned by anyone else even as root — and the error said only
   "Permission denied". The message now names the mode, the owner and the fix
   (`b185463`), rather than adding the capability back.

Still unproven after this: a reboot on a machine that is not a container, and
the full-tunnel client whose *server* is unreachable on a real network (the lab
used a TEST-NET address for the failure case).

## Capacity, measured (2026-11-11) — three ceilings, and the operator path that broke at thirteen

`docs/requirements.md` states 2,000 peers from handshake cost alone and lists
memory per peer, throughput and pps as unmeasured. Two of those now have
numbers, and the ceiling that binds first is not the one the page computes.

**The address plan (measured).** Enrolling peers one at a time into a running
daemon succeeds **253 times** and then stops at the allocator's own boundary —
"the tunnel has no free address left; pass `--address` with one from the
tunnel's subnet, or widen the interface address" — with addresses handed out
10.7.0.2 through 10.7.0.254. The default `10.7.0.1/24` therefore caps a default
install at 253 devices, eight times below the page's stated target, and the
capacity section never mentions addresses. Widening to `/16` lifts it to 65,000
in one config line; nothing in the docs says so.

**Memory per peer (measured).** 6.9 MB resident with no peers, 15.7 MB at
1,000, 24.8 MB at 2,000 → **8.9 KB per peer** idle, ~0.25 ms of startup per
peer. Worst case is the per-peer queue bound (256 packets ≈ 384 KB), which puts
a 3.9 GB host at ~10,000 congested peers. Memory is not the binding constraint
anywhere below that.

**A restart is a two-minute event (measured, then derived).** Handshake cost is
flat across peer-table size — 79.6 ms at a 1-peer table, 79.9 at 100, 80.1 at
1,000, 77.1 at 2,000 (5 samples each, both sides in one process) — so there is
no cliff and the herd is arithmetic: N × per-handshake. At the page's own
18.4 handshakes/s, 2,000 peers re-establish in **~109 s**, and because the loop
is single-threaded that time is taken from the data plane it shares a core
with. A server restart is ~2 minutes of degraded service, not 30 seconds.

**The operator path was broken at thirteen (fixed, `6e4e6d1`).** `peer add`
sends the whole config over the control socket and the daemon stopped reading
at 64 KiB; a hybrid public line is 4,764 bytes, so the fourteenth device failed
with "Connection reset by peer" after the config file had already been written.
The cap is now sized by the 2,000-peer claim with a compile-time assertion.
Found only because the measurement went through the operator path rather than
loading a config file — the file path had always worked.

**Naming rule worth documenting:** peer names must differ in their first eight
characters, because the client interface is `vallum-<name>` and Linux names
stop at fifteen. `device10` and `device100` collide.

## A client restart did not recover (2026-11-11, live, open)

Found while widening the server's prefix on the real deployment — and it is not
the prefix.

The client daemon restarted at 21:22 and never re-established. What the two
ends said, at the same moment:

- **client**: 388 datagrams sent, 0 failed, `window_received=0`, nothing received
  for 21 minutes, `dropped_replay=0`, `dropped_no_session=0` — every counter
  clean, so nothing was arriving at its socket at all.
- **server**: `tcpdump` showed the client's inits arriving (52 and 58 bytes,
  every ~5 s), and the daemon answered **none** of them, with
  `handshakes_refused=0` and every drop counter at zero. Its journal showed one
  establishment ("peer `laptop` established at epoch 0 as Responder") and then
  silence.
- the client's UDP socket existed, `rx_queue=0`, kernel `drops=0` — so the
  server's replies never reached the host.

Reverting the prefix and restarting the server changed nothing. Restarting the
**client** fixed it immediately: 3/3 pings, fresh handshake, `window_received`
moving.

So the failure is in the client's post-restart state machine: it rekeys into a
server that silently ignores it, and only a second restart breaks the loop. That
is roadmap condition 3 ("a dropped connection recovers without a human") failing
in the field for the second time today, with a different shape than the 71-minute
outage: there the client was quiet, here it retries forever and is ignored.

Not diagnosed, and the next session should start from the client's timestamp
guard: the server drops an init whose TAI64N is not newer than the last one it
accepted, and it does so **silently** by design (no oracle). A client whose wall
clock steps back, or whose first init after a restart reuses a timestamp, would
look exactly like this from both ends. The instrument that would separate
"rejected as replay" from "never arrived" is a handshake-level counter — the
data-plane `dropped_replay` does not cover it.

## Hosted-CI assumptions, checked locally (2026-11-11)

The workflow has never run on GitHub's runners, so the checks below were made
against the image it will use, not against the runner itself.

- **`unshare -Urn` works on a stock `ubuntu:24.04`** once the container runtime's
  seccomp profile is out of the way (`--security-opt seccomp=unconfined`), with
  `apparmor_restrict_unprivileged_userns = 0`. My first run reported "Operation
  not permitted" and that was Docker's default profile, not the image — a
  reminder that a container is not a runner. The e2e job's non-root path is
  therefore plausible on `ubuntu-latest`, and its `|| sudo -E` fallback exists
  for the case where it is not; runners have passwordless sudo either way.
- **`sudo` is absent from the base image** and present on GitHub runners, so the
  fallback cannot be rehearsed in a bare container at all.
- Still unproven, and only GitHub can prove it: the first hosted run of
  `ci.yml`, `fuzz.yml` and `release.yml`, and the apt/toolchain steps that have
  never executed outside this host.
